# Database setup

The initial migration targets MySQL/MariaDB. The current local database is `football-api` on MariaDB 10.11.14. The connection URL in ignored `.env.local` preserves the existing credentials and uses the new database name and correct server version.

For a fresh environment, configure `DATABASE_URL` in `.env.local`:

```dotenv
DATABASE_URL="mysql://USER:URL_ENCODED_PASSWORD@127.0.0.1:3306/football-api?serverVersion=10.11.14-MariaDB&charset=utf8mb4"
```

Use the actual server version; for MySQL, use its numeric version without the MariaDB suffix. PHP requires `pdo_mysql`, and the database account needs permission to create the database and tables. The existing Docker Compose service runs PostgreSQL, so it does not supply the server required by this migration.

Run these commands in order:

```bash
composer install
php bin/console doctrine:database:create --if-not-exists
php bin/console doctrine:migrations:migrate
php bin/console doctrine:schema:validate
```

Database creation is separate because migrations connect to an existing database. Doctrine manages its migration history in an additional `doctrine_migration_versions` table.

The initial migration creates:

- `league`: generated ID, name, slug, logo, external league API ID.
- `team`: generated ID, name, logo.
- `game`: generated ID, game time, optional score, required league and home/away team foreign keys; unique home/away/time combination.
- `user`: generated ID, unique username and email, password hash, active flag, points, avatar, creation time.

Columns follow the PHP property types. Game scores may be null before a match finishes. Deleting a referenced team or league is restricted to protect games. IDs are generated by the database, including in fixtures. Tables use utf8mb4.

Optional development data:

```bash
php bin/console doctrine:fixtures:load
```

This purges existing data. The current fixtures add a Premier League record and an active `demo` user (`demo@example.com`, password `demo-password`). Fixtures do not yet seed teams or games.

There is no Guess entity yet, so there is no guesses table. Repository interfaces do not require tables. Rules such as preventing a team from playing itself and requiring nonnegative points are not currently enforced by the domain classes or database. Add them when implementing the relevant behavior.

For subsequent model changes, update the XML mappings, then run `php bin/console doctrine:migrations:diff` and review the generated migration. The initial migration's rollback drops the four domain tables and their data.
